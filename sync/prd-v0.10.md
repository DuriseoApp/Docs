# PRD v0.10 영향 분석

> 상태: 검수 중
> 이전 버전: v0.9 → 새 버전: v0.10
> 브랜치: sync/prd-v0.10
> PR: (PR 완료 후 링크)

이 파일은 `/prd-sync` 팀원들이 읽는 계약이다. 여기 적힌 이름과 할 일을 그대로 따른다.

배경: Server 단위 4(기념일) 범위 점검에서 8개(Server `docs/progress/unit-4.md` "확인 필요" 1~8, 8번은 사실 정정), Android 단위 4(캘린더) 범위 점검에서 14개(Android `docs/progress/unit-4.md` "확인 필요" 1~14)의 빈 곳이 나왔다. 사용자가 **모두 추천안대로** 정했다. PRD에는 제품 결정(D-104~D-114), AC, 화면 목록 비고, 알림 문구 예시, Q-15~Q-17만 넣었다. 기념일 요청·응답 필드, 캘린더용 기념일 항목, 커서·`size` 규칙, 검사 순서 같은 API 표기는 PRD에 넣지 않고 이 파일 3장 "이름 확정"대로 API·ERD·SCREENS에 채운다.

추천안이 디자인 대기나 다른 단위로 미루는 것(알림 버튼, 기념일 링크, [일정 | 메모] 탭, 날짜·시간 선택 임시 처리 등)은 PRD에 범위 메모를 남기지 않고 6장 "문서 밖 결정"에만 적었다. 추천안이 빈 곳을 남긴 부분은 리드가 채웠고 줄마다 **리드 보충** 또는 **리드 지시**라고 적었다. 사람이 정해야 하는 것은 PRD Q-15, Q-16, Q-17이다 (5장).

### 0.3 두 범위 문서 사이 맞춤과 사실 확인

| 항목 | 정한 것 |
| --- | --- |
| 서버 3 "같은 날 자동 기념일이 둘 이상일 수 있다(일수와 주년이 겹침)" | **지금 규칙에서는 생기지 않는다.** 일수 기념일은 처음 만난 날 + 99, 199, …, 999일이고, N주년은 + 365·366일(1주년), 730·731일(2주년), 1095일 이상(3주년부터)이라 같은 날이 없다. 2월 29일 규칙(D-106)을 넣어도 같다. D-106의 순서와 커서 순번은 규칙이 바뀔 때를 위한 안전장치로 둔다. 같은 날 여러 항목은 자동 + 직접, 직접 + 직접에서 실제로 생긴다(Q-15) |
| 캘린더용 항목과 `upcoming` 항목 | 같은 모양 `AnniversaryOccurrence`(3.1). 서버 2 추천안대로 자동의 `repeatsYearly`는 false. **리드 보충**: 지금 API.md는 `upcoming`에서 자동의 `repeatsYearly`를 정하지 않았으므로 `upcoming`에도 같게 적는다 |

| 시간 표기 세 가지 | 날짜 목록 "19:30"(D-113), 상세·작성 "오후 7:30"(D-113), 일정 알림 본문 "1시간 뒤 · 오후 7:30"(8장 기존). 섞지 않는다 |
| 커서 규칙의 범위 | 서버 단위 4에서 정하지만 `cursor`·`size`를 받는 모든 경로(3.2)에 같게 쓴다. Android 단위 5~7도 같은 규칙으로 읽는다 |
| Android 3과 API | `POST /events`의 `reminder`는 늘 null(D-59, API 3.3)이라 작성 화면의 알림은 따로 `PUT`해야 한다. D-108이 그 순서다. 서버 변경 없음 |

모든 경로는 `/api/v1` 아래. "요청 → 성공" 형식과 `?`(선택 필드)는 v0.9의 일정 표와 같다.

| 메서드 | 경로 | 요청 → 성공 | 권한 | FR |

**검사 순서** (서버 5. 일정과 같은 원칙: 권한 없는 사용자에게 필드 오류를 보여주지 않는다)

## 4. 위험 항목

- [ ] DB 마이그레이션 필요: 없음. V1에 `anniversaries`, `ix_anniversaries_space`가 있다. ERD는 설명만 바뀐다
- [ ] 데이터 삭제: 서버 데이터 삭제 규칙 변경 없음. D-111의 삭제는 기기(Room)의 낡은 일정만 지운다
- [x] 권한 변경: 동작 변화는 없고 표기만 바뀐다. 기념일 `PATCH`·`DELETE`에 R-01을 먼저 적용(404), 그 뒤 R-05(403). 검사 순서 R-01 → R-05 → 값 → 날짜 범위 (3.1)
- [x] 앱 호환성이 깨지는 API 변경: 깨지지 않는다. 기념일 API는 Server·Android 구현 전에 처음 정한다. 다만 ① `upcoming` 커서의 정렬 키 문장이 바뀐다(커서는 불투명이라 계약은 그대로) ② `cursor`·`size` 오류가 400으로 새로 정해진다(해당 경로는 아직 구현 전) ③ 자동의 `repeatsYearly` = false를 새로 정한다
- [ ] 개인정보 처리 변경: 없음
- [x] 그 밖: ① 3.4의 동기화 가정(앱이 `SPACE`/`UPDATED`에 기념일을 다시 불러옴)은 Android 단위 7이 연결해야 한다. 빠지면 상대가 처음 만난 날을 바꿔도 자동 기념일이 다음 진입까지 옛 날짜로 보인다 ② 디자인 대기 이미지 6장(요청서 1~5)과 조건부 1장(6), 모두 7장이 나오기 전 Android는 임시 모양으로 만든다 ③ 처음 만난 날이 2월 29일인 커플이 이미 있으면 비윤년 주년 날짜가 정해진다(출시 전이라 영향 없음)

## 5. 열린 질문

- **Q-15 (PRD)**: 같은 날 자동 기념일과 직접 기념일의 순서. 기본값 "자동이 먼저, 그 뒤 직접. 직접끼리는 늘 같은 순서"로 진행한다.
- **Q-16 (PRD)**: NFR-SYNC-02의 "당겨서 새로고침"을 MVP에 둘지. Android 단위 4 추천안은 "지금 만들지 않고 나중에 정하거나 PRD에서 뺀다"까지만 정했다. 기본값 "그대로 둔다(유지). 모양은 요청서 6으로 그린 뒤 만든다"로 진행한다. 빼기로 하면 NFR-SYNC-02 문장을 고치고 요청서 6을 지운다.
- **Q-17 (PRD)**: 새 일정 기본 시간이 다음 날로 넘어갈 때. 기본값 "선택한 날 안에 둔다(시작 23:00, 종료 23:59)"로 진행한다.
- **리드 보충·지시 확인** (기본으로 진행하고, 다르면 알려 주세요):
  1. 자동 기념일의 `repeatsYearly` = false를 `upcoming`에도 적용 (0.3)
  2. 기념일 쓰기에서 `repeatsYearly`가 boolean이 아니면 `INVALID`, `size`가 정수가 아니면 `INVALID` (3.1, 3.2)
  3. 작성·수정 화면에서 하루 종일을 바꾸면 고른 알림이 "없음"으로 (D-107)
  4. 일정 없음(404)을 수정 화면에서 받으면 수정·상세 화면을 함께 닫음 (D-111)
  5. 개인 공간 삭제 본문 "삭제하면 되돌릴 수 없어요."를 PRD에 정함 (Android 7, 리드 지시)
- **참고 (이번 범위 밖)**:
  1. 일정 없음(404)에 기존 문구 "삭제된 일정이에요"(D-43, 알림 목록용)를 쓰는 길도 있다. 이번에는 추천안대로 공통 오류로 정했다.
  2. 끝이 정확히 다음 날 0:00인 시간 일정은 API 3.3의 걸침 조건(`end_at >= 시작`)으로 다음 날 조회에도 들어간다. 앱이 날짜를 나누는 기준(FR-CAL-02 AC5)과 같은지 Android 단위 4 구현 때 확인할 것. Q-17 기본값은 새 일정에서 이 경우를 피한다.
  3. SCR-ANNIV-02에서 공백만 있는 이름의 화면 처리(버튼 비활성 등)와 캘린더 기념일 카드의 "D+N"(자동 기념일)이 그 날 기준인지 오늘 기준인지는 Android 단위 5 범위 점검에서 정한다.
  4. v0.9에서 넘어온 참고: PRD 8장 일정 알림 본문 [알림 시점]의 정시·1일 전·1일 전 오전 9시 문구가 아직 없다 (Server·Android 단위 6·7 전에 정할 것).

- (검수 1회차 뒤) `GET /memos`·`GET /notifications`의 커서 비교 방향(같은 `created_at`일 때 `id` 방향)은 이번에 정하지 않았다. 서버 단위 5·6 범위 점검에서 정한다.
