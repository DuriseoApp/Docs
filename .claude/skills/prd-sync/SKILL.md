# PRD 동기화

이 스킬은 리드(사용자가 연 메인 세션)가 실행한다. PRD의 변경을 파생 문서에 반영하고, 사람은 **승인 한 번과 PR 머지 한 번**만 하게 만든다.

### 점검 모드 (`--dry-run`)

리허설과 정기 점검용이다. 파일을 고치지 않고, 커밋·PR도 만들지 않는다.

1. 0단계의 브랜치·버전 처리는 건너뛴다.
2. `git diff main -- docs/PRD.md`에 변경이 있으면 1~3단계까지만 하고, 영향 분석은 파일로 만들지 않고 화면에만 보여준다.
3. 변경이 없으면 **전체 정합성 점검**을 한다. data, api, screen 팀원을 "읽기 전용 점검" 프롬프트로 만들어 각자 맡은 문서가 현재 PRD와 맞는지 확인해 리드에게 보고하게 하고, review가 문서 사이를 대조한다. 팀원에게 "파일을 고치지 말 것"을 명시한다.
4. 결과를 표로 보고하고 팀원을 종료한다. 고칠 것이 있으면 사용자에게 `/prd-sync`로 반영할지 묻는다.

## 0. 준비

1. `git status`와 `git branch --show-current`로 상태를 본다.
2. PRD 머리의 "문서 버전"을 읽는다 (예: 0.4). 이것이 `<버전>`이다.
3. 브랜치를 맞춘다.
   - `main`에서 PRD를 고친 상태면 `git switch -c sync/prd-v<버전>`으로 옮긴다 (고친 내용은 따라온다).
   - 이미 `sync/prd-v<버전>`이면 그대로 쓴다.
   - 다른 브랜치면 멈추고 사용자에게 묻는다.
4. `main`의 PRD 버전과 같으면 버전을 올리지 않은 것이다. 새 버전 번호(보통 +0.1)를 사용자에게 확인받고, PRD 머리와 12장 변경 이력을 먼저 고친다.
5. `sync/prd-v<버전>.md`가 이미 있으면 이어서 하는 경우다. 그 파일의 "상태"를 보고 해당 단계부터 다시 한다. 팀원이 없어졌으면 새로 만든다.

## 1. 변경 파악

1. `git diff main -- docs/PRD.md`로 바뀐 내용을 본다.
2. 바뀐 항목을 ID 단위로 정리한다: 추가, 수정, 삭제된 FR, AC, SCR, D, NFR, Q, 용어, 권한 매트릭스 줄, 알림 정책 줄.
3. 바뀐 내용 중 사람이 정하지 않은 것(기본값 없는 Q, 모호한 표현)이 있으면 여기서 멈추고 사용자에게 묻는다. 추측해서 진행하지 않는다.

## 2. 영향 분석 파일 작성

`sync/_TEMPLATE.md`를 복사해 `sync/prd-v<버전>.md`를 만들고 채운다. 이 파일은 팀원들이 읽는 **계약**이다. 팀원은 리드의 대화를 볼 수 없으므로 필요한 것은 모두 이 파일에 적는다.

- 바뀐 ID 표
- 문서별 할 일 (ERD, API, SCREENS, 디자인)
- **이름 확정** 표: 새로 생기거나 바뀌는 테이블, 컬럼(타입 포함), enum 값, API 경로·메서드, 요청·응답 필드, 오류 코드, 화면 ID, 주요 문구. 팀원이 서로 다른 이름을 쓰지 않도록 여기서 모두 정한다.
- 위험 항목: DB 마이그레이션이 필요한 변경, 데이터 삭제, 권한 변경, 앱 호환성이 깨지는 API 변경, 개인정보 처리 변경
- 열린 질문 (있으면 3단계에서 사용자에게 묻는다)
- 상태: `승인 대기`

## 3. 승인 (사람)

사용자에게 아래를 보여주고, 끝에 "맞으면 **start**, 고칠 게 있으면 말씀해 주세요."라고 묻고 기다린다. start, 진행, ok처럼 승인하는 말이면 진행한다. **승인 전에는 파생 문서를 고치지 않는다.**

- 바뀐 ID 요약
- 문서별 할 일 한 줄씩
- 이름 확정 표
- 위험 항목
- 진행 방식 (팀 / 리드 단독, 4단계 기준)

사용자가 고치라고 하면 영향 분석 파일을 고치고 다시 보여준다. 승인되면 상태를 `진행 중`으로 바꾼다.

## 4. 진행 방식 결정

- **리드 단독**: 고칠 파생 문서가 하나뿐이거나, 바뀐 ID가 3개 이하이고 문구 수준의 변경일 때. 리드가 해당 에이전트 정의(`.claude/agents/*.md`)의 규칙을 따라 직접 고치고 5단계를 건너뛴다.
- **팀**: 그 밖의 경우.

## 5. 팀 구성과 작업

팀원을 아래 이름과 에이전트 타입으로 만든다. 모델은 각 정의를 따른다.

| 팀원 이름 | 에이전트 타입 | 맡은 파일 |
| --- | --- | --- |
| data | data-architect | docs/ERD.md, docs/erd/erd.html, docs/ERD.png |
| api | api-designer | docs/API.md |
| screen | screen-designer | docs/SCREENS.md, design/change-requests/prd-v<버전>.md |
| review | reviewer | (읽기 전용) |

영향이 없는 문서의 팀원은 만들지 않는다 (예: 화면 변경이 없으면 screen 생략).

각 팀원의 생성 프롬프트에 반드시 넣는다:
- PRD 버전과 영향 분석 파일 경로
- 맡은 파일과, 그 밖의 파일은 고치지 말 것
- 이름이 애매하면 추측하지 말고 리드와 관련 팀원에게 메시지로 물을 것
- git 명령을 쓰지 말 것
- 끝나면 바뀐 ID와 위험 항목을 리드에게 보고할 것

작업 목록:
1. ERD 반영 (data)
2. API 반영 (api)
3. 화면 명세와 디자인 변경 요청서 (screen)
4. 정합성 검수 (review), 1~3에 의존

리드의 규칙:
- 팀원이 끝날 때까지 기다린다. 팀원이 맡은 파일을 리드가 직접 고치지 않는다.
- 팀원 사이에 이름 충돌이 생기면 리드가 결정하고 영향 분석 파일의 이름 확정 표를 고친 뒤 양쪽에 알린다. 사람이 정해야 하는 문제면 멈추고 사용자에게 묻는다.

## 6. 검수 반복

1. review의 보고를 받는다. 상태를 `검수 중`으로 바꾼다.
2. Critical 문제는 담당 팀원에게 고치라고 보낸 뒤 review에게 다시 검사를 요청한다.
3. 3번 반복해도 Critical이 남으면 멈추고, 남은 문제를 PR의 "사람 확인 필요"에 적는다.

## 7. 최종 검사

1. `bash scripts/check-ids.sh`가 통과해야 한다.
2. 모든 파생 문서 헤더가 `PRD v<버전>`인지 본다.
3. 영향 분석 파일의 모든 할 일이 반영됐는지 본다.

## 8. 커밋과 PR

1. 팀원을 모두 종료한다.
2. 변경을 커밋한다. 메시지: `docs(prd-sync): PRD v<버전> 반영`
   본문에 바뀐 ID 목록을 적는다.
3. `git push -u origin sync/prd-v<버전>`
4. `gh pr create --base main`으로 PR을 연다. 본문:
   - 요약 (무엇이 왜 바뀌었나)
   - 바뀐 ID 표
   - 문서별 변경
   - 위험 항목 (있으면 맨 위에 "⚠️ 사람 확인 필요")
   - 검수 결과 (check-ids, review 판정)
   - 사람이 할 일: PR 확인 후 머지. 디자인 변경 요청서가 있으면 머지 후 claude.ai 프로젝트 채팅에서 "디자인 반영해줘"
5. 영향 분석 파일의 상태를 `PR 완료`로 바꾸고 PR 링크를 적은 뒤 같은 브랜치에 커밋·push한다.
6. **머지하지 않는다.** 머지는 사람이 한다.

## 9. 보고

사용자에게 짧게 알린다: PR 링크, 바뀐 ID 수, 위험 항목, 디자인 변경 요청서 경로(있으면 붙여넣을 내용 위치).

## 하지 않는 것

- 3단계 승인 전에 파생 문서 수정
- 동기화 중 PRD 내용 수정 (버전·변경 이력 줄 제외). PRD가 틀렸다고 판단되면 멈추고 사용자에게 묻는다
- 새 디자인 토큰이나 값 만들기
- 기존 ID 삭제나 번호 재사용
- main에 커밋, push, PR 머지
